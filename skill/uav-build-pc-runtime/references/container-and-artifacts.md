# 容器与产物规则

 先读项目约定和现有 Docker/Compose，核实源码位置、Git 状态、子模块、基础镜像、架构、编译器、ROS 版本与磁盘。以用户指定的工作区和提交为准，跨工作区同步前核对差异。构建脚本名字不是可从空机复现的证据。

 以固定 `onboard_computer` 镜像作为构建和运行基线。复现组件在镜像构建阶段复制锁定源码并编译依赖、算法和 Adapter；运行容器不得挂载宿主仓库、源码 workspace、build/install overlay 或依赖目录。接口/ABI 变化连同受影响消费者重编译。基础依赖升级、镜像基线维护与算法镜像迭代分开。
 需要构建应用快照镜像时，将 AS2/PX4 基础镜像作为显式 build arg，而不是默默引用旧发布标签。记录最终基础镜像 ID、应用镜像 ID 和 Dockerfile 的参数；检查镜像内部的安装前缀、消息包和算法节点。多阶段构建的 native 编译镜像与运行镜像都要核实，后者存在不代表前者编译了当前源码。构建成功仍不等于仿真或飞行成功。

 完整锁定的 GPU Python 环境可能包含数 GB wheel；一次缓存未命中会使小源码改动也重新下载全部依赖。构建前确认 Docker daemon/BuildKit 实际代理配置与连通性，保留可追溯的 builder cache，或为固定 lock 准备带校验和的版本化 wheelhouse。缓存与 wheelhouse 只优化获取过程，最终仍要核对镜像内实际分发包与 lock 完全一致；不得为缩短重建而删减运行依赖或放宽版本。
 ## 源码、运行版本与证据对应

 使用项目已有的提交、CI构建号、包版本、镜像digest或清单建立对应，不要求按次复制工作区或保留一组固定目录。存在未提交修改时记录实际差异；仅记录HEAD不能标识工作树构建。

 1. 分别标识编译输入、依赖/工具链、安装产物、实际运行入口及配置。检查容器挂载、overlay顺序和加载位置，避免修改了源码却测试旧程序。脚本或配置变化不一定要求重编译，但改变的行为仍需相应验证。
 2. 增量候选记录复用与重编译的范围、父版本和本次结果。头文件布局或接口ABI变化时按依赖关系核对消费者；父版本成功/失败字段不能直接代表本次构建状态。
 3. 源码清单与生成物清单分开；解释器缓存、构建日志不作为源码修改依据。保留原记录，若旧清单已有混合项，明确分类和差异，不改写旧哈希让新候选通过。
 4. 将构建身份检查结果交给[组件部署](../../uav-package-pc-runtime/SKILL.md)选择运行版本；验收记录另外关联实际运行版本。产物相同、干净构建通过、任务通过是不同结论。

 方法适用于多候选和增量构建，也适用于单一CI产物；不要求新增发布系统。证据与未验证范围见[构建案例](build-cases.md)。

 ## 产物与交付

 涉及 CUDA 模型迁移、独立 uv 环境、权重准备或模型 README/setup 维护时，先读取并执行子 Skill [uav-prepare-cuda-inference](../../uav-prepare-cuda-inference/SKILL.md)，再继续本节交付。具体流程仅在该子 Skill 维护。

 记录 build/install/log 在镜像、容器层还是宿主挂载；长期日志放 `log/<任务>/`，源码留在仓库。镜像重建不会自动更新已有容器，restart 也不切换镜像；替换运行实例属于部署阶段，按授权和任务状态执行。

 交付可执行命令、Dockerfile/Compose、版本与依赖来源、补丁、构建测试日志索引和已知前置条件。失败尝试记入 `skill/temp/<任务>/`，把已验证的修复回馈 Skill，不把某一算法的旧依赖版本规定为所有算法默认。
 ## 基于共享基线的自包含镜像

 记录不可变基础 image ID，并在 Docker build 中复制锁定接口、依赖、算法与 Adapter 源码，
 在目标基线中生成类型支持和 install tree。运行阶段只使用镜像内部产物，不 source 宿主
 overlay，不挂载源码或 build/install。已有目标端依赖仅有规范 msg/srv 定义时，记录版本
 和哈希并在构建阶段重新生成目标架构类型支持；不得复制不同架构的动态库。构建后检查
 镜像内 package prefix、共享库依赖和入口，另以无挂载容器运行验证。

 一个能力拆分为算力端、工作站等多个交付镜像时，对全部会改变运行行为的源码、Dockerfile、
 入口、配置和测试入口建立同一确定性输入清单，将同一摘要嵌入每个角色镜像。启动验收前
 重新计算当前输入摘要，并逐个比较镜像标签；任一角色缺少标签或摘要不同都必须重建，不能
 把来自不同源码状态的镜像拼成一轮证据。摘要清单可以排除不参与构建或运行的说明文档和
 能力卡，但须记录各角色基础镜像、最终 image ID 及其职责，避免只锁算法镜像而遗漏任务端。

 ROS shell 环境脚本不一定支持 Bash nounset。入口可在 source ROS/AS2/colcon setup 时暂不启用 `set -u`，加载后再启用；用真实目标镜像构造节点，而不只做 Python 语法检查。Python ROS 节点避免以 `handle`、`clients` 等 Node 只读属性命名自己的状态；目标 rclpy 的真实构造检查能检出这类问题。

 固定镜像缺少组件运行所需的第三方依赖、且按约定不重建镜像不新增基础环境依赖时，优先在组件包内做最小等价实现（保持被消费的原接口面不变），并在测试期与真实原库对照断言语义等价（原库仅测试期安装，运行时零依赖），作为编号偏离记录；CityNav 的 networkx 替换（包内最小无向图 + `test_graph_equivalence.py` 对照）为该模式的已验证实例。

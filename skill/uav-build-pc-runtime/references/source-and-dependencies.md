# 源码与依赖规则

 1. 上游源码用完整提交锁定，保留许可。联合算法只保留一份源码。独立构建环境按实际 ROS 依赖拆分，不强行混装发行版。
 2. 明确所有基础镜像来源和构建入口；本地已有但仓库无法生成的镜像列为前置依赖，不宣称完整独立复现。交付记录镜像 ID/digest、平台架构及源码状态。
 3. 依赖使用可解析版本和校验和。短提交失效时核查 API 需求和历史兼容性，说明替代依据；不能静默改为最新。vendor 归档保留来源、许可、锁定提交和 SHA256。
    Python 算法不能只锁顶层 requirements：从一次成功环境提取完整解析版本，形成受跟踪的 lock/constraints，并核对镜像内实际分布与锁文件无缺失、额外项或版本差异。目标 ROS 发行版自带 pytest/插件时，显式验证 pip 升级后的 hook 兼容性；算法库声明 `pytest>=...` 可能把 Humble 的 `launch_testing` 升坏。
 4. 兼容问题优先在当前项目的 `ros2_adapter/`、插件、配置或启动层解决，保持锁定上游源码不变。ROS 1 算法必须源码迁移到 Humble，不能用 Bridge/Proxy 或额外挂载 ROS 1 runtime 规避。项目自有适配代码直接维护在主仓库；如果修复必须改变上游算法或依赖的实现，则在可追溯 Fork 中实施。所有 Fork 必须作为 Git 子模块接入，由 `.gitmodules` 记录可访问 URL、由父仓库 gitlink 锁定修改提交；构建直接消费该子模块，不复制 Fork 源码，也不只靠依赖参数锁定。参考 `upstream/` 与实际构建输入明确分开，区别算法输出语义修复和编译兼容修复，不要为了编译成功删掉算法所需能力。

    构建侧补丁只可用于定位问题、验证候选修复或从历史部署迁移，必须检查上下文与版本匹配；它不是完成复现后的最终源码来源。迁移到 Fork 时核对补丁后的完整 Git tree 与 Fork 提交一致，包括空文件删除、权限和重命名；确认目标提交可从远端获取，删除重复应用步骤并记录源码归属。主仓库能克隆不代表依赖提交已发布；实际构建依赖算法子仓时，先发布依赖提交，再发布引用它的主仓库提交。迁移会改变构建来源，即使树内容相同也要重跑来源、构建和受影响运行验证，不能直接沿用旧补丁版本的成功结论。
 5. 核对 Docker COPY、依赖安装、colcon/catkin 包选择和测试范围；新目录不会自动进入镜像。限定构建并发，说明 native CPU 优化的移植限制。
 6. 构建并执行与改动相应的安装/加载检查。明确命中缓存意味着相关测试未重跑；需要重新验证时有针对性地失效缓存。
 现有子模块 checkout 与 gitlink 不一致时，先保存实际版本和修改；可将主仓库提交及所需 gitlink 源码导出到独立构建上下文，逐项记录来源和后续补丁。运行入口记录的工作树版本与实际构建输入分别标注，不能将旧 checkout 的 HEAD 当作新镜像的来源。先独立编译原生算法，再编译接入层；是否封装应用快照由交付需求决定，便于区分依赖、算法和接入层失败。

 目录迁移时区分仓库相对路径、ROS 包名和镜像内安装路径，不能全局替换同名字符串。移动 ROS 包后同时核查 Docker COPY、colcon 包发现、测试依赖、Compose 构建上下文及 Python 的仓库根路径计算。`.gitignore` 不会自动取消已有产物的 Git 跟踪；迁移日志时保存原始内容并检查索引。

 只有官方上游无需修改、而项目正在实现独立 ROS 移植或 Adapter 时，才可把项目自有实现维护在主仓库；必须保留来源、基线提交、许可证和与上游的职责边界，并使用不含参考子模块源码的干净上下文验证没有隐藏依赖。该做法不得用于承载 Fork 修改：一旦修改上游实现，源码必须回到 Fork 子模块，主仓库仅保留适配层。
 ## 禁止绝对路径工作区复用

 catkin devel-space、生成脚本和插件元数据可能嵌入宿主绝对路径，因此不得把旧 catkin
 workspace 以双路径挂载方式作为复现或交付方案。ROS 1 项目先迁移为 ament/Humble；其他
 依赖从锁定源码在 Docker build 的规范路径重新构建。镜像检查应搜索宿主路径、catkin
 devel 引用和未解析 RPATH；发现任何一项均判定镜像非自包含。

 ## 同名 ROS 包隔离

 不同算法包含同名 ROS 包时，源码目录分开不能消除包发现与运行时解析冲突。构建时隔离包发现范围、build 和 install，运行时检查所加载 overlay 的包前缀，避免选中另一个算法的同名包。

# 组件打包、注册与部署管理

## 输入与边界

读取项目约定、实际实现、构建产物、能力卡片与验收结论。组件清单回答“安装运行什么”，能力卡片回答“提供什么、如何选择使用”。不因生成了清单就声称已有注册中心、调度器或自动回滚实现。

部署边界遵循[四方职责](../../docs/项目简介.md#deployment-roles)：算法与 AS2 能力由算力角色提供，工作站经 ROS 调用已就绪能力；部署管理与任务执行分别管理生命周期。记录角色共置和历史拓扑的差异。共享约定更新不触发其他项目迁移；只修改本轮明确范围内的组件。

## 清单内容

复用项目已有格式；没有格式时采用明确版本的 YAML 初稿，不冒充 AS2 原生规范。至少说明：

- 稳定组件 ID、版本、源码/补丁、许可证、镜像与架构、完整依赖及外部前置条件。
- 提供的 capability IDs 和 `cards/` 路径；共享进程、共享设备与不可独立启停的能力组。
- 入口、配置、标定要求、挂载、持久化目录、命名空间、时钟、端口、算力和传感器要求。
- 生命周期、依赖就绪条件、健康/数据新鲜度、停止确认、失败与回滚处理。
- 状态/TF 发布权及资源冲突、用户权限、已验证场景和证据版本。
- 验证阶段使用可枚举状态（如 `build-verified`、`interface-verified`、`partial`、`reproduced`）；只有端到端验证 Skill 规定的全部适用测试在清单所指同一版本上通过并有证据时才能使用 `reproduced`/`success`。GPU 必需但未运行、下游未消费、shadow gate 失败或证据缺失时保持 `partial` 或明确失败状态。

## 部署流程

Inference 组件部署需分别记录 ROS Adapter 与模型 worker 的环境、启动入口和可达地址；本机回环仅在同一网络命名空间内可用。算法上游路径与推理模块路径分别声明，每模型的 uv 环境不与 ROS overlay 混合。健康状态区分 HTTP 进程可用、模型加载预热完成与 ROS 消费者实际可调用，不能仅凭 ROS Service 存在宣称就绪。

组件包含 CUDA 模型且需迁移或准备环境/权重时，先读取并执行子 Skill [model-migration-cuda](../model-migration-cuda/SKILL.md)，消费其准备入口和验证结果，再继续组件部署；模型准备细节仅在该子 Skill 维护。

1. 检查目标环境、依赖、输入表示与消费者匹配。缺少传感器或有效标定不能仅启动空进程后标健康。
2. 先隔离验证启动、真实输入消费与输出新鲜度，再接入既定消费者。发现现有能力冲突时不要默认覆盖。
3. 依赖按就绪状态启动，不只依赖固定 sleep；健康区分进程存活、算法初始化、数据有效和任务可用。
4. 切换权威状态或运动提供者时，检查消费者停止、旧发布者退出、TF 与时间连续性和新来源就绪。若尚无无缝切换机制，明确要求停止任务后切换，不虚构热切换。
5. 更新失败时按明确版本恢复，并再次检查发布权与健康；回滚可能不能保留地图/估计内部状态，须说明重初始化影响。

组合状态组件应把本地控制状态与全局校正列为两个独立依赖，并分别声明失效影响。例如低频 SLAM 退出时可冻结 `map -> odom`，但只有经故障飞行验证后才能声称高频本地 `odom -> base_link` 足以支持受控降落；本地估计器失效不能被同一结论覆盖。清单的停止顺序、健康条件和能力卡片必须反映这种分层，而不是笼统写成“状态估计可用”。

## 交付

提供清单、启动/停止/检查命令、参数示例、更新回滚方法、能力卡片关联及证据索引。已有部署脚本优先复用；不要替用户擅自部署到飞行设备或修改运行中的系统。

能力卡片分工由卡片编写 Skill 负责；没有可用 Skill 时按本节关系检查而不阻塞。记录进入 `skill/temp/<任务>/`，产物进入 `log/`。本初版定义交付要求，不意味着当前 Model Hub 的注册、安装和回滚系统已实现。

## 共享 GPU 主机与跨系统迁移

读取现有共享资源说明并先盘点进程、容器、GPU、端口和挂载权限；查询被拒绝不能记为空闲。使用任务自有目录、容器身份、DDS domain 与证据目录，源码与共享安装默认只读；host-net 不提供端口隔离，仍需逐项核对 RPC、HIL、DDS/Agent 与 worker 端口。

模型 venv、ROS overlay 与图形会话分别定位。宿主检查 venv 时核对 pyvenv.cfg 和解释器链接目标，容器中再验证该目标和动态库实际可执行；不把 Windows 环境复制为 Linux 环境。DISPLAY/授权与私人路径使用本地配置，模型准备细节继续由模型子 Skill 维护。

**双角色容器模板。** 仿真平台的 compute（推理/规划）与 sensor（传感器适配/桥接）是两个独立容器，各自连 AirSim RPC；clock 容器可跨飞行不重启，但 vehicle/sensor 在 AirSimNH 被杀期间若保持运行，`docker start` 是 no-op（内部 RPC 已死），必须显式 stop+start。跨轮恢复顺序见验收 Skill（先停 sensor→停 vehicle→重启 AirSimNH→等 GPU 释放→恢复 vehicle→确认 ESTAB→恢复 sensor→重建 compute）。

**env-only 运行时配置。** `AS2_EXECUTION_BACKEND`、`FLOWPILOT_MAX_INPUT_AGE_S` 这类运行时开关不写进镜像，运行时用 `docker run -e` 或 Compose `environment:` 传入；镜像内只保留算法默认值。源码补丁（如 compute.py 读取 env 并透传给节点）随源码打入镜像，运行时阈值由 env 调节，不因改阈值重建镜像。

按记录的容器 ID/标签、PID、可执行路径、启动时间和参数确认资源归属，再有界停止。模糊 `pgrep -f` 可能匹配检查命令自身，不能据此决定清理。当前构建若存在 PX4/AirSim 单连接限制，按实测顺序停止自有 PX4、重启自有 AirSim、再启动 PX4；仅使用本次启动后的就绪日志。AS2 状态机残留则另行复位算力实例，不能用重启一个容器假定全栈干净。

具体 Demo 必须交付其目标系统的正式启动/检查/停止入口。已在某服务器任务目录运行，不等于新 Linux 主机可从仓库独立复跑；Windows Docker Desktop 入口也不等于原生 Linux 编排。FlowPilot 的正式入口、依赖和当前入口缺口见 [验收参考](../uav-sim-e2e-validation/references/flowpilot-acceptance.md)，不以旧任务目录脚本作为本 Skill 的执行依赖。

# 组件交付案例

案例解释遗漏如何发现，不要求其他项目采用相同目录、容器角色数或启动步骤。

## 实验入口归入正式组件

本补充来源于 RACER 单机 Docker 固化：正式源码干净构建、logger 初始化与基础导航节点清理分别暴露了旧实验依赖和入口遗漏。单机结果不证明其他算法、跨机/板端部署或跨版本回退可直接复用；这些分支仍需按各自矩阵验证。

## 当前工作区与已验收基线

RACER后续诊断源码已进入工作区，组件和能力卡片仍标识旧短程基线，同时扩大范围配置保存在独立候选。核对确认它们不是同一个可互换版本，交付分别列出匹配入口和证据。旧版本身份检查通过不等于执行了回退飞行；当前诊断候选飞行通过也不能继承旧版本两轮重复验收。见[版本选择与矩阵](../../../deployment/airsim/demos/racer_multi_flight/DELIVERY_REVIEW.md)。

## Demo 单独选择检测后端

切换单个 Demo 的模型时，一并核对 worker 启动脚本、端口、`model_id`、ROS facade 服务类型、Detect backend/query/阈值、参数文件及全部消费者 overlay。共享 Harness 保留原默认后端，由 Demo 显式选择；不同生成接口不得叠加旧 workspace。

入口先提供无副作用的启动计划检查，再以真实 ROS 节点构造确认参数生效、服务类型匹配且没有旧后端节点；文本检查不能替代真实构造。区分复用的 worker 与本轮拥有的 worker，异常清理只停止后者。模型身份或 CUDA 不匹配时失败，不自动切换模型；新部署默认值与历史模型验收分别标记。
